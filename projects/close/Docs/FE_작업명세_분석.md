## Phase 1 — 핵심 커머스 및 송출 (Must-be) | 예상 5~6주

> 이 Phase 없이는 서비스 불가. RN 신규 개발이 포함되어 가장 무거운 Phase.

### 1-1. IVS 송출 RN 앱 신규 개발 `8~12일`

**내용**: 판매자가 폰으로 방송 송출하는 RN 전용 앱 구현. 시청 플레이어 RN 연동 없음.

> **플랫폼 확정**: 시청은 웹(모바일 브라우저) 유지. RN = 송출 전용.  
> **⚠️ IVS 아키텍처 [젬또리 2026-07-01]**: Low-Latency HLS 유지. Real-Time 전환 비권장 (3~4천 명 규모에서 시간당 $300+).

**웹 (기존 코드 개선)**:
- `AdminLive.tsx` 카메라/오디오 기기 선택 UI 완성 (기존 주석 처리된 코드 복원)
- `Live_Component.tsx` 버퍼링 감지 UX 개선

**RN 송출 앱 (신규) — 경로 분기**:

| | 경로 A (커뮤니티 패키지) | 경로 B (Native Bridge) |
|:---|:---:|:---:|
| 방법 | `amazon-ivs-react-native-broadcast` | iOS Swift + Android Kotlin 직접 작성 |
| 공수 | **8일** | **12일** |
| 리스크 | AWS 비공식, 버전 호환 | iOS/Android 각각 디버깅 |

- 카메라/마이크 권한 처리 (iOS `Info.plist`, Android `AndroidManifest.xml`)
- 방송 시작/종료, 기기 선택, 프리뷰 캔버스 → RN View 연결
- **1주차 초반 커뮤니티 패키지 검증 → 경로 확정**

**미확인**: AWS IVS 채널 타입/레이턴시 모드 [미검증] — 백엔드/인프라팀 확인 필요

---

### 1-2. 영상-데이터 싱크 (상품 팝업 타이밍) `3~5일`

**내용**: 라이브 영상 프레임 이벤트에 맞춰 상품 팝업이 지연 없이 노출되도록 싱크 최적화

**웹**: `Live_Component.tsx`에 `PlayerEventType` 이미 있음 → `TEXT_METADATA_CUE` 이벤트 기반 팝업 트리거 추가  
**RN**: `amazon-ivs-react-native-player`의 동일 이벤트 수신 후 팝업 트리거 신규 구현

**기술 포인트**:
- Socket.io 재고 변경 이벤트 ↔ IVS 타이밍 이벤트 **이중 싱크** 충돌 방지
- HLS 버퍼(3~5초)로 인한 팝업 노출 지연 → 서버 타임스탬프 기준 오프셋 보정 [젬또리 2026-07-01]
- 웹 vs RN HLS 버퍼 차이로 팝업 시점이 다를 수 있음 → 플랫폼별 오프셋 분기 필요

**리스크**: 기기/네트워크별 레이턴시 차이로 QA 기간 길어질 수 있음

---

### 1-3. WebSocket 실시간 채팅 / 접속자 수 `3~5일`

**내용**: Socket.io 기반 채팅 렌더링 + 접속자 수 카운팅 — 웹 개선, RN 신규

**웹**: `ChatComponent.tsx`(IVS Chat SDK) 기본 동작 중 → 안정성 개선 및 추가 기능 준비  
**RN**: 웹 `ChatComponent.tsx` 참조하여 RN용 신규 구현

**기술 포인트**:
- RN에서 소켓 연결 시 앱 백그라운드/포어그라운드 전환 시 재연결 처리
- 채팅 리스트 FlatList 가상화 필수 (수백 개 메시지 렌더링 성능)
- 접속자 수: 소켓 이벤트 수신 → 숫자 뱃지 실시간 업데이트

---

### 1-4. 어드민 기능 제어 `3~5일`

**내용**: 웹 대시보드(상품관리 등 풀기능) + RN 모바일(송출 관련 제한 기능)으로 역할 분리

**플랫폼별 범위 확정**:

| 기능 | 웹 | RN 모바일 |
| :--- | :---: | :---: |
| 상품 관리 (등록/수정/재고/가격/순서) | ✅ | ❌ |
| 주문 관리 / 대시보드 | ✅ | ❌ |
| 라이브 송출 시작 / 종료 | ✅ | ✅ |
| 송출 장치 선택 (카메라/마이크) | ✅ | ✅ |
| 라이브 예약 추가 / 취소 | ✅ | ✅ |
| 라이브 뱃지 설정 | ✅ | ✅ |
| 판매창 색감 변경 | ✅ | ✅ |

**웹 기술 포인트**:
- `Live_Manage.tsx` 기반 어드민 제어 기능 개선 (기존 코드 있음)
- 상품 노출 순서 Drag & Drop: `react-beautiful-dnd` 적용
- 가격/재고 수정: API 성공 후 소켓으로 시청자 화면 동기화 (낙관적 업데이트)

**RN 기술 포인트**:
- 1-1 송출 화면과 통합된 컨트롤 패널 (오버레이 형태, 화면 전환 최소화)
- **장치 선택**: `IVSBroadcastClient` 디바이스 목록 API로 카메라/마이크 전환 UI
- **라이브 예약 추가/취소**: 캘린더 또는 날짜 피커 기반 일정 관리 UI
- **뱃지 / 색감 변경**: 방송 중 실시간 반영 → API 호출 후 소켓으로 시청자 화면 동기화

## Phase 2 — 운영 자동화 및 성과 고도화 (Performance) | 예상 3~4주

> Phase 1 완료 후 착수. 결제 고도화 가장 무거움. PG사 확정 선행 필요.

### 2-1. 카카오싱크 라우팅 최적화 `2~3일`

**내용**: 인앱 브라우저 환경에서 카카오싱크 로그인 리다이렉트 이탈 없이 처리

**웹**: `kakaoban_page.tsx`에 `kakaotalk://web/openExternal` 방식 구현됨 → 카카오싱크 1 Click 가입 플로우 연결 및 최적화  
**RN**: `Linking.openURL` + `@react-native-seoul/kakao-login` SDK 적용, OAuth 리다이렉트 URL 스킴 등록

**미확인**: 카카오싱크 비즈니스 계약 상태 — 계약 미완료 시 이 항목 블로킹

---

### 2-2. 결제/장바구니 고도화 `7~10일`

**내용**: 혼합결제(카드+코인) + 득템 리스트 일괄 결제 장바구니 로직 신규 개발

**웹**: `Buy_Modal.tsx` 단건 즉시 구매만 있음 ("장바구니 개념 아님" 주석) → 일괄결제 신규 추가  
**RN**: 동일 결제 로직 신규 구현 (웹 Hook 재사용 가능 부분 최대화)

**기술 포인트**:
- **혼합 결제**: 카드 + 코인 동시 사용 금액 계산 UI. `CoinManage/` 기존 코드 참조
- **득템 리스트**: 방송 중 찜 → 방송 종료 후 일괄 결제 (전역 상태 관리 — Zustand 권장)
- 결제 직전 재고 재확인 API 호출 (실시간 재고 변동 대응)
- PG사 SDK 연동 — 웹뷰 방식 vs Native 방식은 PG사에 따라 결정

**리스크**: **PG사 미확정 — 착수 블로킹**. PG사 확정 즉시 착수.

---

### 2-3. 채팅 고도화 `3~5일`

**내용**: 공지 고정, 음소거, 관리자 매크로 — 웹/RN 모두 신규 기능

**웹**: `ChatComponent.tsx` 위에 추가 구현  
**RN**: 1-3에서 구현한 RN 채팅 컴포넌트에 동일 기능 추가

**기술 포인트**:
- **공지 고정**: IVS Chat 메시지 타입 분기 → 공지 수신 시 상단 고정 뷰 렌더링
- **음소거**: 유저 ID 로컬 블랙리스트 → 수신은 유지, 렌더링에서 필터링
- **매크로**: 어드민 페이지 템플릿 목록 탭 원터치 전송

## Phase 3 — 마케팅 확장 및 게임화 (Attractive) | 예상 2~2.5주

> 웹/RN 모두 신규. 디자인 에셋 준비 상태가 일정 변수.

### 3-1. 인터랙션 / VFX 구현 `5~7일`

**내용**: '가자! 게이지', 완판 VFX, 황금 티켓 팝업 등 방송 화면 인터랙션 — 신규

**기술 포인트**:
- **웹**: `lottie-react` / CSS keyframes + `framer-motion`
- **RN**: `lottie-react-native` — 동일 `.json` 에셋 재사용 가능 (웹/RN 공유)
- 영상 오버레이 레이어 위 애니메이션 렌더링 — 비디오 성능 영향 없도록 레이어 분리
- 게이지: 소켓으로 판매량/목표치 수신 → Progress Bar 실시간 업데이트

**리스크**: Lottie 에셋 디자이너 준비 여부 [확인 필요]. 없으면 직접 구현으로 +2~3일

---

### 3-2. 맞춤형 알림 / 등급 뱃지 렌더링 `2~3일`

**내용**: 초대 링크 입장 시 맞춤 환영 알림, 유저 등급별 뱃지 표시 — 신규

**기술 포인트**:
- URL 파라미터(`?ref=xxx`) 파싱 → 소켓 이벤트로 맞춤 환영 메시지 트리거
- RN Deep Link 진입 시 파라미터 보존 (iOS Universal Link / Android App Link)
- 등급 뱃지: API `grade` 필드 기반 채팅 닉네임 옆 아이콘 조건부 렌더링

---

### 3-3. 취소 티켓 로직 (프론트 방어선) `2~3일`

**내용**: 방송 중 유저별 제한적 취소 — 티켓 차감 방식 프론트 방어 로직

**웹**: `Delivery_Info_Modal.tsx` 내 취소 로직 주석 처리 상태 → 주석 해제 + 티켓 차감 플로우 연결  
**RN**: 동일 로직 신규 구현

**기술 포인트**:
- 남은 취소 티켓 수 API 조회 → 버튼 활성/비활성
- "티켓 1장 차감" 확인 모달 → 서버 응답 후 상태 업데이트 (낙관적 업데이트 지양, 중복 클릭 방지)

## IVS 아키텍처 의사결정 기록

> 젬또리 조사(2026-07-01) 기반. PM 확인 후 확정.

### Low-Latency(현행) vs Real-Time(WebRTC) 비교

| 항목 | Low-Latency (현행 유지) | Real-Time (WebRTC) |
| :--- | :--- | :--- |
| 레이턴시 | 3~5초 | 300ms 미만 |
| 동시 시청자 | 수백만 명 (CDN 무제한) | Stage당 최대 25,000명 |
| 비용 (4천 명 × 1시간) | $100~300 내외 | **$300 (시간당 고정)** |
| 모바일 배터리 | 하드웨어 가속, 부담 적음 | CPU/GPU 소모, 발열 위험 |
| 네트워크 불안정 | 버퍼링으로 자동 보정 | 즉각 화면 깨짐/끊김 |
| VOD 다시보기 | S3 자동 녹화 | Server-Side Composition 별도 필요 |
| RN 송출 SDK | 커뮤니티 패키지 / Native Bridge | 공식 없음, WHIP 또는 Native Bridge |

### 결론: Low-Latency 유지 + 채팅 타임스탬프 보정 [젬또리 2026-07-01]

3~4천 명 라이브 커머스에서 비용·안정성·모바일 UX 모두 Low-Latency 우위.  
채팅 3~5초 싱크 차이는 서버 타임스탬프 보정으로 처리.
